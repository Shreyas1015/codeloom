# codeloom 0.5 — one-step setup and Claude-checked PR reviews (design)

Date: 2026-11-16 · Status: agreed with the author in conversation · Builds on 0.4.1.

Why: the author tried the 0.4 PR view on a real backend PR and could not understand it — it showed
structure (30 boxes of raw names, 14 tables) but not what the PR does or what to check. What a reviewer
needs is a five-part summary. For demo-shop, a PR that makes customer saving atomic would read:

> **What it does:** saves a customer in one step, so a retry no longer creates a duplicate … **Where it
> matters:** `POST /api/customers` and the CSV import … **What it writes:** only the `customers` table …
> **⚠ Before deploying:** needs a migration first … **Code to check:** `CustomerUpsertService.upsert`
> (new) and the 2 lines that call it.

Principle: codeloom does the work (no AI); Claude only checks and corrects it, reading a small packet,
so it costs few tokens. Claude is never run without asking.

## 1. One-step setup: `codeloom init`

Interactive when stdin/stdout are a TTY; `--yes` takes every default (CI, scripts).

1. **Repos** — list what was found; repos with the same git remote URL are grouped and only the one on
   the default branch (else the first) is pre-selected (a folder of ~20 checkouts can hold several copies
   of the same repo). The user
   can toggle repos. Writes `codeloom.workspace.json` (`links: []` always present).
2. **Commit or keep local** — "Commit codeloom's files with your code?" Yes (today's behaviour: `.gitignore`
   line, post-commit hook) / **Keep local** (add `.codeloom/` — and `codeloom.workspace.json` when the
   root is itself a repo — to each repo's `.git/info/exclude`; no `.gitignore` edits; hook off). Default:
   commit for a single repo, keep local for a folder of repos.
3. **Index** — runs `codeloom index` with progress.
4. **Claude Code** — if the `claude` CLI is on PATH: "Connect Claude Code?" (default yes) → `.mcp.json`
   entry pinned to this codeloom version. Then "Let Claude name your journeys now? (uses your Claude
   Code)" (default no) → headless run (§3).
5. **Dashboard** — "Open the dashboard?" (default yes) → `codeloom dashboard`.

Prints a 4-line summary of what it did and the next command. Re-running `init` on a set-up workspace
offers only what is missing.

## 2. The PR draft: `codeloom review` (no AI)

Same command and flags; new default layout (the 0.4 layout stays as `--format full`).

**Folders of repos** (e.g. a folder of ~20 checkouts): a PR belongs to one repo, so `codeloom review --repo <id> --base <ref>` (and
`--packet`, `--check`) diffs only that repo (`merge-base(<ref>, HEAD)` in it); every other repo is read as
it is checked out now. With one repo, or when the current directory is inside a workspace repo, `--repo`
is optional. 0.4's "the workspace root must be a git repo" error is replaced by this.


- Status line: `_Draft by codeloom — not checked._` (or `_Checked by Claude <date>._`, §3).
- **What it does:** `_(Claude fills this in when it checks the PR.)_`
- **Where it matters:** the entry points that reach a changed function — routes, pages, queue consumers —
  named by journey when named, at most 5 then "+N more".
- **What it writes:** tables/queues the *changed* functions write (db stops with op insert/update/
  delete/upsert, publish) on their own chains after the changed stop; "Reads only:" on one line after.
- **⚠ Before deploying:** one line per detected risk — migration / schema files changed (`migrations/`,
  `database/migrations/`, `*.sql`, `schema.prisma`, `drizzle/`), env files (`.env.example`, `env.ts`, a new
  `process.env.X` / `NEXT_PUBLIC_X` read), Docker/CI files. Omitted when none.
- **Code to check:** changed functions (new / changed / deleted) with +/− counts, at most 8.
- **Diagram:** only the changed path — entry point → … → changed function → tables it writes; ≤ 8 nodes,
  then "+N more". Labels escaped as today.
- Files on no chain: one line ("Also changed: 12 files — docs, tests, config").

## 3. Claude checks: `check-pr`

- **Packet** (`codeloom review --packet`, also the MCP tool `pr_check_packet`): the draft as JSON + for
  each changed function only its changed hunks (≤ 60 lines each, ≤ 400 total) + commit subjects and
  bodies (≤ 40 lines) + the facts the draft cites (names that exist). Capped at 24,000 characters
  (~6k tokens); what is cut is listed.
- **Prompt** `check-pr` (also used headless): verify every draft line against the packet; fix what is
  wrong or missing; write "What it does" in 1–2 plain sentences; keep each section ≤ 3 lines; never name
  a function, route or table that is not in the packet; save with `save_pr_review`.
- **Tool** `save_pr_review({ head, whatItDoes, whereItMatters?, writes?, beforeDeploying?, codeToCheck?,
  notes? })`: `head` must equal HEAD; every name must exist in the packet's facts, else refused with the
  bad names; saved to `<ws>/.codeloom/reviews/<head>.json` (local only, git-ignored / excluded).
- `codeloom review` renders a saved review for HEAD instead of the draft, status "Checked by Claude".
- **Headless:** interactive `codeloom review` asks "Let Claude check this PR now? (uses your Claude
  Code)"; `--check` runs without asking. Runs `claude -p <check-pr prompt with the packet inlined>
  --allowedTools mcp__codeloom__save_pr_review` in the workspace root, so Claude needs no other tool
  calls. Prints the checked block. Without `claude` on PATH: prints the prompt to run instead.

## 4. Proxies (a Next.js app calling its backend through its own `/api/core/*` proxy)

Workspace repo entry gains `proxies?: [{ from: string /* URL prefix, e.g. "/api/core" */, to: string /*
repo id */, stripPrefix?: boolean /* default true */ }]`. A UI call in that repo whose URL starts with
`from` is matched against `to`'s routes with the prefix stripped (exact/param confidence as today; the
proxy route's own chain stays). Validated (unknown repo id → data error). Docs + workspace-file reference.

## 5. Acceptance (the author's judgement is the bar)

- A real backend PR like the customer-saving one above, run in a folder of repos (`--repo <id>`, other
  copies not selected): the checked block reads like the example above.
- A real Next.js PR whose calls go through its own `/api/core/*` proxy, with `proxies` → the backend:
  journeys touched > 0; the block names the flow the PR changes.
- Setup: a fresh `npx codeloom init` on a copy of a folder of ~20 checkouts reaches a working dashboard
  and a connected Claude in one run, with the duplicate copies unticked.
- Token use: a `check-pr` run on that backend PR sends ≤ 24k characters of packet.

## Not in this version
Summaries in CI; the hosted snapshot opening on the summary; `codeloom snapshot` for folders of repos;
Bitbucket automation.
