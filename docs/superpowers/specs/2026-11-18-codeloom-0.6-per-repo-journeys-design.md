# codeloom 0.6 — index each repo, connected journeys, one-command PR pages, Claude fixes the map (design)

Date: 2026-11-18 · Status: draft for the author's review · Builds on 0.5.0.

## The goal (the author's five points, verbatim)

1. As a new developer how the journey would be: come in, see 10 repos, then go in each repo and run
   `codeloom index` in each of the 10 repos.
2. Then if all are single repos intended, then it would work properly, as frontend and backend would be
   connected.
3. Then if all are microservices, then we need to connect it properly and show the user journeys and all.
4. Usually then while working, if any PR is created, one single command shows what the PR does, the
   journey and all — chain, table and all that properly.
5. Usually through Claude Code, we need to check all of it and correct, ask the user questions properly
   — like "is this frontend connected to the backend of this", "which are microservices in these ones" —
   and Claude will properly update the whole codeloom dashboard for it, without wasting many tokens by
   starting from scratch.

Each section below is one point. A version is done only when all five work, end to end, on the test setup
in §6.

## 1. Index each repo on its own

- `cd <repo> && npx codeloom index` works in any git repo with no setup: no workspace folder, no workspace
  file, no `init` required (init stays as the optional guided path).
- The repo's own map stays in `<repo>/.codeloom/` as today (graph, endpoints: routes served, HTTP calls
  made, tables, queues published and consumed).
- **Group.** Each indexed repo registers itself in a machine-local registry,
  `<CODELOOM_HOME or ~/.codeloom>/registry.json`: `{ repos: [{ id, path, remote, group, indexedAt,
  role? }] }`. Repos are grouped automatically by their git remote's host and owner
  (`github.com/acme`, `bitbucket.org/acme`), so a company's repos form one group and unrelated projects on
  the same machine stay apart. `codeloom index --group <name>` overrides; a repo with no remote gets the
  group of its parent folder name. Duplicate checkouts of the same remote: the most recently indexed one
  is the group's copy for that repo; others are listed as copies and ignored for linking.
- Group-level data (chains, journeys, tours, specs, views, answers from §5) lives in
  `<home>/groups/<group>/`. A repo moved or deleted is dropped from the registry on the next run that
  notices it (`codeloom doctor` reports it).
- The existing workspace-folder mode keeps working unchanged (a folder with `codeloom.workspace.json` is
  its own group).
- `codeloom dashboard` run inside any repo opens its group's map.

## 2. Separate frontend and backend repos connect by themselves

- After a repo is indexed, codeloom re-links the whole group (re-reads each repo's saved endpoints; it
  never re-parses the other repos): UI calls are matched to every group repo's routes with the 0.5 rules
  (exact / param / guess, proxies, folded client factories, `apiBase`).
- Hints are found without config where the code shows them: an env var or host in a call's base that
  names another repo (`CORE_API_URL`, `core.example.com`) is matched to that repo by its id, package name
  and remote name; a Next.js proxy route that forwards to an env-var base is treated as a proxy rule for
  the repo that env var points at. Unclear cases are not guessed: they become questions in §5.
- Acceptance: indexing the frontend repos and backend repos of the test setup one by one gives at least
  the journeys the 0.5 single-folder workspace gave (290 complete), with no hand-written config.

## 3. Microservices connect into user journeys

- **Service-to-service HTTP**: calls made by a backend repo are matched to other group repos' routes like
  UI calls, so a chain continues `UI → service A route → handler → HTTP call → service B route → handler →
  table`.
- **Queues**: RabbitMQ through amqplib, including calls through the repo's own wrapper functions and
  classes (`QueueService.publish("invoice.created", …)`), exchanges with routing keys, and consumers
  registered through wrappers. A publisher in one repo and a consumer in another with the same
  queue/exchange+key are linked; the chain continues into the consumer's handler and tables. Unresolved
  names are never guessed; they become §5 questions.
- Journeys may span any number of repos; the dashboard lanes show the repo of every stop.
- Acceptance: on the test setup, at least one real chain crosses two backend repos over HTTP and at least
  one crosses over a queue; `check` reports queue counts > 0 for the repos that use RabbitMQ.

## 4. One command on a PR

- `npx codeloom pr` in the repo where the PR branch is checked out (the 0.5 follow-up already in
  progress): re-indexes this repo and re-links its group, builds the draft (what it writes, before
  deploying, code to check, where it matters), asks "Let Claude check this PR now?" (or `--check`), and
  opens one local page: Claude's "What it does" and the checked facts on top, then the journeys, chains
  and tables the PR touches (across repos, using §2–§3), then the changed functions with diffs and the
  diagram. It also prints the block for pasting into the PR description.
- Works the same in a group (§1) and in a workspace folder (`--repo`).

## 5. Claude checks the whole map, asks, fixes — cheaply

- `codeloom gaps` (and the MCP tool `map_gaps`) lists only what codeloom could not settle, ranked by how
  many journeys each affects, capped (≤ 40 items, ≤ 12,000 characters): repos with no connection to the
  rest of the group; calls whose base is an unknown env var or host; calls matching no route; routes no UI
  or service calls; queues with a publisher but no consumer (or the reverse); ambiguous matches (two repos
  could serve a call); repos whose role is unclear (UI / API / worker / library / not part of this
  system). Each item carries the evidence (file:line, the literal or env name) and a suggested question.
- Prompt `map-interview` (and `codeloom ask`, which starts it in Claude Code with the same consent rules
  as 0.5): Claude reads `map_gaps`, groups related gaps, and asks the user short questions one at a time
  ("Does `CORE_API_URL` point at the core-service repo?", "Is the worker repo a separate service that
  consumes `invoice.created`?"). It may read small code snippets through the existing tools to propose an
  answer, never the whole repo.
- Tool `save_map_answers`: writes answers to the group's answers file — env/host → repo mappings, proxy
  rules, manual links, repo roles, "ignore this repo", queue name aliases, "this call is external". Every
  repo id, route, env name and queue must exist in the map (refused otherwise, as in 0.5).
- After each saved answer codeloom re-links (no re-parse) and the dashboard updates live; `map_gaps`
  shrinks. Answers are reused by every later index of any repo in the group, so nothing is asked twice.
- Token budget: a full interview on the test setup sends ≤ 40,000 characters of codeloom output to Claude
  in total (gap list + snippets), measured and reported.

## 6. Test setup and acceptance (the author's judgement is the bar)

The author's real machine: one folder of ~10 private repos (3 web UIs, 5 backends, some duplicate
checkouts) plus a partner backend that lives in a different folder and calls one of the backends over
HTTP. Nothing from those repos is ever copied into this repo; fixtures use demo-shop names.

- Point 1: a fresh `CODELOOM_HOME`; `codeloom index` run inside each repo, one by one, in any order; no
  other command.
- Point 2: ≥ 290 complete UI → API → DB journeys across the group, with no config written by hand.
- Point 3: a partner → backend HTTP chain and a queue chain appear; RabbitMQ repos report queues.
- Point 4: `codeloom pr` on two real PRs (one backend, one partner) opens a page the author can read
  without explanation, with Claude's summary on top.
- Point 5: `map-interview` asks fewer than 15 questions, each answer visibly changes the dashboard, and
  `codeloom gaps` is shorter afterwards; the token budget holds.

## Not in this version
Sharing group data with the team (committing it); non-JS/TS journeys; Kafka/SQS/Redis queues; Bitbucket or
GitHub automation of `codeloom pr`.
