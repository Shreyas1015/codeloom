# codeloom v0.2b — tours and progress (design)

Date: 2026-11-05 · Status: approved by the author in brainstorming ("looks good, whatever is recommended") ·
Builds on v0.2a (map accuracy) and the v0.1 spec §4–§6 (data files, MCP, dashboard) which already sketch tours
and progress. Approved mockups: `.impeccable/mocks/screens/codeloom-screens.html` screens 3 (Tour mode) and
5 (Progress). Design system: `DESIGN.md`.

## Goal

Turn a journey into a guided tour you can walk, and track honestly how much of the codebase you understand:
seen → toured → understood, where "understood" is only earned by passing a check that the agent judges against
the code, and goes stale when that code changes.

## 1. Tours (team knowledge, committed)

- File: `.codeloom/tours/<journeyId>.json` in the workspace root (committed, like journeys.json; written only
  through MCP `save_tour`).
- Shape (`version: 1`, zod-validated, sorted):
  - `journeyId`, `writtenAt` (ISO; the only timestamp — tours are agent content, not derived files),
    `writtenAtCommit` per repo (`{ [repoId]: sha }`).
  - `stops: [{ chainId, stopIndex, key: <stopKey>, fileHash, explanation (markdown, ≤ 1500 chars) }]` — Flow
    phase; `key` is the shared `stopKey` (lane, repo, file, line, symbol) so tours survive renumbering.
  - `dataJourney: { input: string (JSON/text sample), steps: [{ stopKey, sql?: string, note: string }], output: string }`.
  - `fileNotes: [{ repo, file, notes: [{ kind: "trap" | "note", text }] }]`.
  - `check: [{ question, expected: string[] (key points the agent judges against) }]` — exactly 3.
- `fileHash`: sha256 of the stop file's content at writing time. A stop whose current file hash differs is shown
  "may be out of date" in Tour mode; the tour stays usable.
- MCP:
  - `build_tour_context { journey }` → per stop: code slice (± 30 lines, capped), types it uses, SQL/ORM call
    detail for db stops, request/response shapes found in the code (zod schemas, TS types, validators), the
    stop's neighbors (method edges from v0.2a), and the current file hashes — capped under 1 MB like other tools.
  - `save_tour { journey, tour }` → validates (stops must exist in the journey; exactly 3 check questions; sizes),
    computes `fileHash`/`writtenAtCommit` itself (the agent never supplies hashes), writes atomically.
  - Prompt `write-tour { journey }`: call `build_tour_context`, write plain-language explanations per stop, a data
    journey with a realistic sample, traps per file, 3 check questions with expected key points; save with
    `save_tour`; never invent stops or code.

## 2. Progress (personal, never committed)

- File: `~/.codeloom/progress/<workspaceId>.json` where `workspaceId` = sha256 of the workspace file's `name` +
  sorted repo ids (stable across clones/paths) — first 16 hex chars. Respect `CODELOOM_HOME` env override (tests).
- Shape (`version: 1`): per journey id:
  `{ seenAt?, touredAt?, understoodAt?, understoodAtCommit?: { [repoId]: sha }, stopHashes?: { [stopKey]: fileHash }, checks: [{ at, questions, answers, verdict: "pass" | "fail", notes, commit }] }`.
- Levels: **seen** — the journey was opened in the dashboard; **toured** — all four tour phases were viewed in Tour
  mode (needs a tour); **understood** — set only by `record_check` with verdict `pass`.
- Re-walk rule (spec §4): a journey is **needs re-walk** when any stop's current file hash differs from
  `stopHashes` at `understoodAt`; only those stops are listed. Re-walking (opening those stops in Tour mode) then
  passing `check-me` again restores "understood".
- MCP:
  - `get_progress { repo?, area? }` → per journey: level, needs-re-walk stops, last check; totals per repo and area
    (`understood / total`), and what is left.
  - `record_check { journey, questions, answers, verdict, notes }` → appends to `checks`; on `pass` sets
    `understoodAt`, `understoodAtCommit`, `stopHashes` (computed by codeloom, not the agent). The only way to set
    "understood".
  - Prompt `check-me { journey }`: read the tour's 3 questions (or write 3 from the code if there's no tour), ask
    the user one at a time in chat, judge each answer against the code and the expected points, explain gaps, then
    call `record_check` with the verdict (pass = all 3 acceptable). Never record a pass the user didn't earn.

## 3. Dashboard

- **Tour mode** `/journeys/:id/tour?phase=&stop=`: phases Flow → Data journey → File notes → Check yourself, ←/→
  between stops, phase tabs, the stop's code (Shiki) beside its explanation, "may be out of date" markers. Check
  yourself shows the 3 questions, the last result and history, and a "Check me in Claude" button that copies
  `/mcp__codeloom__check-me <journey id>`. No tour yet → an empty state with a copy button for
  `/mcp__codeloom__write-tour <journey id>`. Finishing the four phases marks "toured".
- **Progress** `/progress`: per repo and per area — understood / toured / seen of total (`ProgressStrip`), the
  needs-re-walk list (journey + changed stops), recent checks (pass/fail, date), and "what's left" sorted by area.
- Home and Journey gain the parts v0.1 omitted: understood % in the header, a three-segment progress strip per
  journey row, the Journey nameplate level badge, and the Continue band resumes the next unfinished tour stop.
- New write endpoints (the only ones; same session token, same 127.0.0.1/Host/cookie rules):
  `POST /api/progress/seen { journey }`, `POST /api/progress/toured { journey, phases }` — they never set
  "understood", never write journeys or tours. Read: `GET /api/progress`, `GET /api/tours/:journeyId`.
- Live updates: the watcher also watches `.codeloom/tours/` (`tours` change key) and the progress file
  (`progress` key).

## 4. Errors and edge cases

- Journey renamed/merged/split (new id): tours and progress keyed by the old id are shown as "for an older journey"
  with a one-click hint to re-run `write-tour`; never silently lost. (Aliases from v0.1 H11 apply to chains, not
  journeys.)
- Corrupt progress file: reported with a clear message; never overwritten silently (`doctor` checks it).
- A tour that references stops no longer in the journey: those stops are listed as "removed" in Tour mode.

## 5. Testing

- Unit: tour/progress schemas, `workspaceId`, re-walk computation, `save_tour` validation, `record_check` the only
  path to understood, endpoints (auth, no other writes), MCP contracts (each tool valid + invalid), prompts text.
- Dashboard: Tour mode phases/keyboard/empty states, Progress screen, Home/Journey additions; contrast and focus per
  DESIGN.md; Impeccable review of the two new screens against the mockups.
- e2e (Playwright, local Chromium on 127.0.0.1): save a tour for a demo-shop journey via the in-process MCP client,
  walk it in Tour mode → toured; `record_check` pass → understood; edit a stop's file and re-index → needs re-walk on
  that stop only.

## Out of scope

Spec matching and custom views (v0.3), team-shared progress, hosted anything.
