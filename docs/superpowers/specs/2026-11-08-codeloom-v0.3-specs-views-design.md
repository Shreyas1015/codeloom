# codeloom v0.3 — specs per journey + views Claude can customise (design)

Date: 2026-11-08 · Status: approved by the author in brainstorming · Builds on v0.2 (main 49010a3).
Covers the author's original points 3 ("per tour/feature: spec present or not") and 4 ("using Claude they can
update the view"). v0.1 spec §4–§6 already sketch `match_specs`, `save_view`/`list_views`, SpecBadge and `/views/:id`.

## 1. Spec candidates (no AI, no network)

Built on every `codeloom index`, written to `<ws>/.codeloom/spec-candidates.json` (generated, committed,
deterministic, sorted; `version: 1`).

- **Docs:** files in each repo matching `docs/**`, `**/README*`, `**/adr/**`, `**/*.{md,mdx,txt}` (respecting the
  repo's ignore rules; skip `node_modules`, `.codeloom`, build output; ≤ 512 KB per file). A doc is a candidate for a
  journey when it mentions, as whole tokens: a route path of the journey (`POST /api/customers` or `/api/customers`
  with `:param`/`{param}`/`[param]` normalised), a page path, a table name, a queue name, or a stop symbol
  (`CustomerService.create`; bare method names only when ≥ 6 chars and not built-in names). Evidence per candidate:
  `{ kind: "route"|"page"|"table"|"queue"|"symbol", term, file, line }` (first 5 hits + total count). Score =
  weighted hits (route 3, page 3, table 2, queue 2, symbol 1) — used only for ordering.
- **Tickets:** `git log --name-only --format=…` per repo over the files under the journey's stops (last 500 commits
  per repo); keys found in commit subjects/bodies and branch names from merge commits matching the workspace
  `specs.ticketPattern` (default `\b[A-Z][A-Z0-9]+-\d+\b`) minus `specs.ignorePrefixes` (default `["CVE","UTF","ISO","RFC","SHA"]`).
  Evidence: `{ commit (short), file, subject (≤ 120 chars) }` (first 5 + count). Score = number of distinct commits.
- Workspace file gains optional `specs: { docs?: string[] (extra globs), ignoreDocs?: string[], ticketPattern?: string, ignorePrefixes?: string[] }` (validated; a bad regex is a data error).
- Per journey: `{ docs: Candidate[], tickets: Candidate[] }` capped at 20 each, sorted by score desc then ref.

## 2. Confirmed links (Claude confirms)

- `<ws>/.codeloom/specs.json` (`version: 1`, committed, team-shared; written only by MCP `save_spec_links`):
  `{ journeys: { [journeyId]: { links: [{ kind: "doc"|"ticket", ref, reason, savedAt }], checkedAt } } }`.
  `ref` = `repo:path` for docs, the key for tickets. A journey with `checkedAt` and no links = "no spec" (confirmed
  none); without `checkedAt` = "not checked".
- MCP: `match_specs { journey }` → candidates + evidence + short snippets (± 3 lines around doc hits) (< 1 MB);
  `save_spec_links { journey, links }` (each doc ref must exist in the repo; each ticket key must match the pattern;
  `[]` allowed = confirmed none; replaces that journey's entry; sets `checkedAt`); `list_specs { repo?, area? }` →
  per journey state + coverage totals.
- Prompt `match-specs { journey? }` — for one journey or all unchecked ones: call `match_specs`, read candidate docs
  and the journey's code (`explain_context`), keep only links that really describe this journey with a one-line
  reason, save with `save_spec_links` (save `[]` when none fit). Never invent refs.
- Spec state per journey: `linked` (≥ 1 link) · `candidates` (not checked, has candidates) · `none` (checked, no
  links, or not checked and no candidates).
- Journeys renamed/merged (new id): their spec entries show under "for an older journey" (like tours).

## 3. Views (fixed widget set)

- `<ws>/.codeloom/views/<id>.json` (`version: 1`, committed; written only by MCP): `{ id, title, description?, widgets: Widget[] }` (≤ 24 widgets).
- Widgets (zod discriminated union, unknown types rejected):
  - `counts { show?: ("files"|"pages"|"routes"|"tables"|"queues"|"journeys"|"understood"|"specLinked")[] }`
  - `journeys { title?, filter?: { area?, repo?, spec?: "linked"|"candidates"|"none", level?: "none"|"seen"|"toured"|"understood"|"rewalk", confidence?, complete? }, sort?: "name"|"area"|"stops"|"confidence"|"progress"|"spec", limit?: 1..200 }`
  - `map { repo, overlay?: "layer" | "journey:<id>" , dir? }`
  - `progress { by?: "repo"|"area" }`
  - `checks { limit?: 1..50 }`
  - `specCoverage { by?: "repo"|"area" }`
  - `note { markdown (≤ 4000 chars, rendered without raw HTML) }`
- MCP: `save_view { view }` (validates; id `[a-z0-9-]{1,40}`), `list_views`, `delete_view { id }` (not `home`). Prompt
  `make-view { request }`: turn a plain request into a view using only the widget set, save it, and tell the user the
  dashboard link `/views/<id>`.
- `home` view: if `views/home.json` exists and is valid, Home renders it; otherwise Home renders the built-in v0.2
  layout. `codeloom views list` and `codeloom views reset <id>` (deletes the file; for `home` restores the built-in
  default) are new CLI commands.
- Dashboard: `/views/:id` route; rail "Views" section listing views; a broken view file renders an error card (never
  breaks the shell) with `codeloom doctor` hint. The dashboard never writes views or specs. Live updates: `views` and
  `specs` change keys.

## 4. Dashboard spec UI

- `SpecBadge` per journey (Home rows, Journey nameplate, views): linked (viridian), candidates waiting (ochre), no
  spec (oxblood — its one permitted use besides errors), not checked (muted).
- Journey screen "Specs" tab: linked docs (open in the code viewer, read-only, path safety as `/api/code`) and ticket
  keys with Claude's reason; candidates (if not checked) with evidence; a copy button for
  `/mcp__codeloom__match-specs <journey id>`.
- Home filter gains "Spec"; Progress screen gains spec coverage.

## 5. Testing

- Unit: doc candidate matching (whole tokens, params normalised, bare-symbol rule), ticket extraction (pattern,
  ignores, merge-branch names), determinism of spec-candidates.json, specs.json validation, view schema, home
  fallback, CLI `views` commands, endpoints/MCP contracts, prompts text.
- Fixtures: demo-shop gains a `docs/` folder and committed history with ticket keys (generic `SHOP-12` style) — in
  test setup, never the author's repos.
- e2e: Claude (in-process MCP client) saves spec links and a "No-spec audit" view → both appear live; a broken
  `home.json` → Home falls back with a notice.
- Acceptance re-run on the author's local workspace copy (privacy rules unchanged): how many journeys get candidates.

## Out of scope

Fetching ticket text (codeloom stays offline; Claude may summarise tickets with its own tools into the `reason`),
free-form/HTML panels, chart query language, mobile shell.
