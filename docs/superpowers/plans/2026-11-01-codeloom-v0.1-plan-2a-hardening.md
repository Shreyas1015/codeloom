### H4: Resolve bare imports through tsconfig `baseUrl`

**Problem:** in `realworld-nest`, imports like `import { UserEntity } from "user/user.entity"` rely on `compilerOptions.baseUrl: "src"`. `loadAliases` handles `paths` but not plain `baseUrl`, so the import resolves nowhere and DI/class links break.

**Requirements:**
- `loadAliases` (or the resolver) also treats `baseUrl` as a root: a bare specifier resolves to `<tsconfig dir>/<baseUrl>/<specifier>` when that file exists (same extension/index rules as relative imports). Packages (no matching file) stay unresolved.
- `paths` take precedence over `baseUrl`, matching TypeScript.
- Works for nested tsconfig files in monorepos (the tsconfig nearest the importing file wins).

**Acceptance tests:** baseUrl `src` + `import { X } from "user/user.entity"` resolves to `src/user/user.entity.ts`; `import express from "express"` stays unresolved even with baseUrl set; `paths` beats `baseUrl` on overlap.

### H5: TypeORM injected repositories as DB access

**Problem:** Nest services use `constructor(@InjectRepository(UserEntity) private readonly userRepository: Repository<UserEntity>) {}` and call `this.userRepository.save(...)`, `findOne(...)`, `delete(...)`. The DB adapter only knows `getRepository(X)`.

**Requirements:**
- In the DB adapter, a member call on `this.<field>` where the field is a constructor parameter property or class property typed `Repository<E>` / `MongoRepository<E>` / `TreeRepository<E>` (or decorated `@InjectRepository(E)`) is a DbAccess with `model: E`, op from the existing REPO_OPS map (add `findOneBy`, `findAndCount`, `exist`/`exists`, `preload`, `merge`→update as needed), `via: "typeorm"`.
- `E` → table via the existing `@Entity` model defs (`@Entity("name")` / `@Entity({ name })` / class-name default).
- Also `this.<field>.createQueryBuilder(...)` → read on E.
- Respect the dependency gate (`typeorm` or `@nestjs/typeorm` present).

**Acceptance tests:** the constructor-property form, a class-property form, the `@InjectRepository` decorator form with an untyped field, and a non-repository field (`private readonly http: HttpService`) producing no DbAccess.

### H1: Router-level mounts and honest confidence

**Problem:** `realworld` builds `const api = Router(); api.use("/articles", articlesRouter); …; const routes = Router(); routes.use("/api", api); export default routes;` and the app does `app.use(routes)` (no prefix). codeloom reads no router→router mounts and reports `/articles` as `exact`.

**Requirements:**
- `detectMounts` records `<router>.use(prefix?, target)` for any receiver that is a router (created by a router factory, or a generic router name in a backend file, or imported from a file that exports a router), not only `app`. A `use(target)` with no prefix is a mount with prefix `""`.
- Mount targets resolve through imports to the file and exported router name; a default-exported router counts.
- `effectiveRoutes` composes router→router chains across files (existing cycle/depth/dead-end handling applies).
- **Confidence:** a route whose router is exported (or default-exported) from its file but has no resolved mount chain is `mountsKnown: false` (so its matches are at most `guess`), never `exact`. A route on a router that is used directly by the app/server file (`app.get`, or `app.use(router)` resolved) stays known.

**Acceptance tests:** the realworld three-level shape (app → routes `/api` → api `/articles` → articles router `GET /:slug`) gives `/api/articles/:slug` with `mountsKnown: true`; the same router exported but never mounted gives `mountsKnown: false`; a prefix-less `app.use(router)`; a mount via a default-imported router.

### H2: HTTP wrapper functions and superagent

**Problem:** `realworld`'s UI calls `requests.get("/articles?limit=10")`, where `requests = { get: url => superagent.get(`${API_ROOT}${url}`).then(responseBody), post: (url, body) => superagent.post(`${API_ROOT}${url}`, body)…, del: … }`. codeloom sees neither superagent nor the wrapper.

**Requirements:**
- HTTP adapter: recognise `superagent` (and `request`-style `agent`) calls: `superagent.get|post|put|patch|del|delete(url)`; dependency or import gated.
- **Wrapper inference** (in the linker, using the code index + resolver, not the per-file adapter): a function (or object method) whose body makes an HTTP call whose URL is `${BASE}${param}` / `BASE + param` / `param` alone, where `param` is one of its own parameters, is an HTTP wrapper. Its method is the inner call's method (or derived from the wrapper's own method name `get|post|put|patch|delete|del` when the inner call uses a variable method). Every resolved call to the wrapper with a literal/template URL argument becomes an HttpCall at the caller (path from the argument via `pathPattern`, base from the wrapper's base expression), with confidence no better than `param`.
- Record wrapper-derived calls so `linkUi` treats them like adapter calls; mark them (e.g. `via: "wrapper"`) for diagnostics.
- Keep the existing direct-call detection unchanged.

**Acceptance tests:** the realworld `requests` object shape; a plain wrapper `function apiGet(path) { return fetch(`${API}${path}`) }` called as `apiGet("/users")`; a wrapper called with a non-literal argument stays unresolved; a function that hard-codes its URL is not a wrapper.

### H3: Handlers reached through JSX props; warn on unreached calls

**Problem:** in `prisma-rest-nextjs`, fetch calls live in handlers like `const submitData = async (e) => { await fetch("/api/post", …) }` used as `<form onSubmit={submitData}>`. JSX attributes are not call sites, so no page reaches the call and the chain is dropped without a warning.

**Requirements:**
- Code index: an identifier (or `this.x` / `obj.x`) referenced as a JSX attribute value or passed as a JSX prop (`onClick={handle}`, `onSubmit={(e) => submit(e)}` already a call) is recorded as a reference edge from the enclosing component to the referenced function (e.g. `CallSite` with `kind: "jsx-ref"`), resolved like a call. Plain `{handler}` children are not edges.
- The UI reverse walk follows these edges; their hop confidence is at most `param`.
- `codeloom check`: an HTTP call that reaches no page and no route gets a `ui-unreached` item ("call at file:line is not reached from any page"), listed in its own group; it does not change chain buckets.

**Acceptance tests:** the prisma `submitData`/`onSubmit` shape reaches its page; an inline arrow prop calling a named handler reaches it; a function referenced only in a non-JSX context is not an edge; `check` lists an unreached call.

### H6: Next.js pages-router API method detection

**Problem:** `pages/api/post/[id].ts` handles only `DELETE` via `if (req.method === "DELETE")` but is recorded as `ANY`.

**Requirements:** for pages-router API handlers, collect methods from `req.method === "X"` / `!==` guards and `switch (req.method) { case "X": … }` in the default-export handler; emit one route per method found; fall back to `ANY` when none are found. App-router route files are unchanged.

**Acceptance tests:** single `if` → that method only; `switch` with two cases → two routes; a handler that never checks the method → `ANY`.
