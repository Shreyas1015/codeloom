# codeloom v0.3 — specs per journey + custom views — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. UI tasks also use the `impeccable` skill (craft floor before UI edits).

**Goal:** Implement `docs/superpowers/specs/2026-11-08-codeloom-v0.3-specs-views-design.md`.

**Architecture:** A new indexer step builds `spec-candidates.json` from repo docs and git history (no AI, no network). New store modules for confirmed spec links (`specs.json`) and views (`views/<id>.json`), written only through new MCP tools. The dashboard reads them via new GET endpoints, renders a SpecBadge everywhere journeys appear, a Specs tab on Journey, a `/views/:id` route and a widget renderer; Home renders `views/home.json` when valid.

### Task 1: Spec candidates in `codeloom index` (spec §1)
- `packages/cli/src/specs/candidates.ts`: doc scanning (globs, ignores, size cap, whole-token matching with param normalisation, bare-symbol rule reusing the built-in name list), ticket extraction from `git log` (pattern/ignores from the workspace `specs` config; merge-commit branch names), per-journey candidates (cap 20, sorted), evidence. Runs after the linker in `codeloom index`; writes `<ws>/.codeloom/spec-candidates.json` with `writeJsonIfChanged`. Workspace schema gains `specs` config (bad regex → data error).
- demo-shop fixture gets `docs/customers.md` (mentions `POST /api/customers`, `customers` table) and the test helper commits history with `SHOP-12`-style keys.
- Tests: matching rules, ignores, determinism (warm/cold byte-identical), performance on a 2,000-file synthetic repo (< 5 s).

### Task 2: Spec links + views store, MCP tools, prompts, CLI (spec §2, §3)
- `store/specs.ts` (schema, read, `saveSpecLinks` with validation), `store/views.ts` (widget union schema, read/list/save/delete, home fallback helper), MCP tools `match_specs`, `save_spec_links`, `list_specs`, `save_view`, `list_views`, `delete_view`; prompts `match-specs`, `make-view`; CLI `codeloom views list|reset <id>`; doctor checks specs.json and views; catalogue/contract tests, README MCP + CLI sections, docs test, pack-test catalogue (now 25 tools).
- Reads `spec-candidates.json` produced by Task 1 (agree on its schema: put `SpecCandidatesFileSchema` in `store/schemas.ts` in Task 1; Task 2 imports it — if Task 1 hasn't merged yet, define it identically and the controller reconciles).

### Task 3: Server endpoints + live keys
- `GET /api/specs` (per journey state + links + candidates summary), `GET /api/specs/:journeyId` (full candidates + links), `GET /api/views`, `GET /api/views/:id` (validated; invalid → 200 with `{ error }` so the UI can show an error card), `GET /api/docs?repo=&file=` (doc text, path-safe like /api/code, refuses `.codeloom`), api-types; watcher keys `specs` (spec-candidates.json, specs.json) and `views` (views/); dashboard hooks + invalidation.

### Task 4: Spec UI (spec §4)
- `SpecBadge` (gallery component, tokens per DESIGN.md), on Home rows, Journey nameplate, view journey widgets; Journey "Specs" tab; Home "Spec" filter; Progress spec coverage.

### Task 5: Views UI (spec §3)
- `/views/:id` route, widget renderer for every widget type (reusing Home/Map/Progress pieces), safe markdown for notes, error card for broken views, rail "Views" section, Home renders `home` view when valid else the built-in layout (with a quiet notice when `home.json` is invalid).
