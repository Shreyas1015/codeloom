# codeloom 0.6 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. UI tasks also use `impeccable`.

**Goal:** Implement `docs/superpowers/specs/2026-11-18-codeloom-0.6-per-repo-journeys-design.md` — the author's
five points, end to end.

**Architecture:** A machine-local registry groups repos by git remote owner; `codeloom index` inside any repo
indexes that repo, registers it, and re-links its whole group from saved endpoints (no re-parse). The group
behaves like today's workspace (`loadWorkspace` returns it, with absolute repo paths and a data root under
`<home>/groups/<group>/`). Hints from env-var/host names, service-to-service HTTP and wrapped RabbitMQ queues
extend linking across repos. `codeloom gaps` + a `map-interview` prompt + `save_map_answers` let Claude settle
the rest with the user; answers live in the group and are re-applied on every link. `codeloom pr` (point 4,
already built on feat/codeloom-pr) reads the group.

## Global Constraints
- All 0.5 constraints still bind (/Users/shreyashgurav/orca/projects/codemap/.superpowers/sdd/v05-constraints.md):
  personal identity, no work names anywhere in the repo (demo-shop names in fixtures/tests/docs), precision
  first (never invent links — unresolved = a §5 gap, not a guess), eval gate unchanged or better, commit by path,
  never `git stash`, nobody pushes to main, ask before push/publish.
- Workspace-folder mode (a folder with `codeloom.workspace.json`) keeps working exactly as in 0.5.
- No re-parsing of other repos when one repo is indexed; linking reads saved endpoints/graphs only.
- `map_gaps` ≤ 40 items and ≤ 12,000 characters; a full interview on the test setup ≤ 40,000 characters sent.
- Claude is never started without consent (0.5 rules); answers are validated (every repo id, route, env name,
  queue must exist in the map).

## Waves
Wave 1 (parallel): Task A (registry + groups + per-repo index + group dashboard), Task B (RabbitMQ wrappers,
exchanges, routing keys — adapter only). Wave 2 (parallel): Task C (cross-repo hints + service-to-service HTTP +
cross-repo queue links), Task D (gaps + map-interview + save_map_answers + re-link). Wave 3: Task E (merge with
feat/codeloom-pr; `codeloom pr` uses groups) and acceptance on the author's machine (spec §6).

### Task A: Registry, groups, per-repo index (spec §1)
- `packages/cli/src/workspace/registry.ts`: read/write `<home>/registry.json` (zod schema, atomic write);
  `groupOf(repoAbs)` from the remote (host + owner; `--group` override; no remote → parent folder name);
  duplicate checkouts of one remote → newest indexed is the group's copy, others recorded as `copyOf`.
- `loadWorkspace(start)`: when no workspace file is found above `start` and `start` is inside a registered (or
  being-registered) git repo, return the repo's group: `root` = `<home>/groups/<group>/`, repos with ABSOLUTE
  paths (audit every `join(root, repo.path)` → a resolver that accepts absolute paths), ids unique in the group.
- `codeloom index` in a repo: index that repo (as today), register it, then re-link the group from saved
  endpoints of every member (no re-parse of others); print what got connected. `--group <name>`.
- `codeloom dashboard` / MCP `serve` inside a repo serve its group. `doctor` reports moved/deleted repos and
  drops them with `--fix`.
- Tests: two demo-shop repos (web, api) indexed separately with a fresh CODELOOM_HOME → chains link web→api;
  order-independent; duplicate checkout ignored; unrelated remote owner → separate group; workspace-folder
  mode unchanged (existing tests green).

### Task B: RabbitMQ through wrappers (spec §3, adapter part)
- `packages/cli/src/adapters/queues.ts`: follow the repo's own wrapper functions/classes around amqplib
  (`publish(queue, msg)`, `QueueService.publish("invoice.created", …)`, `consume(queue, handler)`), exchanges
  (`assertExchange`, `publish(exchange, routingKey)`), `bindQueue(queue, exchange, key)`; record publisher /
  consumer with queue or exchange+key and the handler; literal names only (const / enum / static readonly
  resolved within the file or one import hop); never guess.
- Tests with demo-shop-shaped wrappers (a `QueueService` class, a function wrapper, an exchange with routing
  keys); eval gate unchanged.

### Task C: Cross-repo hints, service-to-service HTTP, cross-repo queues (spec §2–§3)
- Base hints: env var / host in a call's base → a group repo by id, package name or remote repo name
  (`CORE_API_URL` → `core-service`); applied only when exactly one repo matches; else a gap.
- Backend repos' outgoing HTTP calls are matched to other repos' routes like UI calls (chains continue
  handler → call → other repo's route → handler → table).
- Queue links across repos: publisher ↔ consumer by queue, or exchange+routing key via bindings.
- Tests: demo-shop web + api + billing worker as three separately indexed repos (fresh CODELOOM_HOME): UI → api
  → HTTP → billing route chain; api publish → billing consume chain; ambiguous env name → no link (gap).

### Task D: Gaps, map interview, answers (spec §5)
- `packages/cli/src/map/gaps.ts`: compute the ranked gap list (spec §5 kinds) with evidence and a suggested
  question; `codeloom gaps` (CLI, `--json`) + MCP `map_gaps`; caps from Global Constraints.
- Group answers file `<group>/answers.json` (zod): env/host→repo, proxy rules, manual links, repo roles,
  ignore repo, queue aliases, external call. MCP `save_map_answers` validates names against the map, saves,
  re-links (no re-parse) and returns the gaps it closed. Answers are applied on every link.
- Prompt `map-interview` + `codeloom ask` (consent as in 0.5; headless isolated like check-pr but this one is
  interactive — run in the user's Claude Code session via the prompt; `codeloom ask` prints the exact
  `/mcp__codeloom__map-interview` to run when not interactive). The prompt: one question at a time, propose an
  answer from evidence, save, report what changed.
- Dashboard: live update after an answer (existing live-reload keys); `codeloom gaps` count on Home.
- Tests: gaps for an unknown env base, an orphan queue, an unconnected repo; answer each → gap closed, chain
  appears; invented names refused; size caps.

### Task E: `codeloom pr` on groups + acceptance (spec §4, §6)
- Merge feat/codeloom-pr (after its review fixes); `codeloom pr` inside a grouped repo uses the group for
  journeys across repos.
- Acceptance on the author's machine (spec §6), run read-only against throwaway copies, with a fresh
  CODELOOM_HOME: index each repo one by one; report journeys, cross-repo chains, queues, `codeloom pr` on two
  real PRs, and an interview run (questions asked, characters sent). Nothing from those repos enters this repo.
