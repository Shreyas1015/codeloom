# codeloom v0.1 — Release plan — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A published-ready `codeloom` npm package that installs fast with no native build step, carries the core engine, the grammars and the dashboard inside it, is documented, proven by a tarball install test in CI, and has passed the v0.1 acceptance run on the author's real workspace — then (only with the author's approval) published to npm and the GitHub repo made public.

**Architecture:** Only `packages/cli` is published (spec §2). A release build bundles the cli's own code and the private `@codeloom/core` source into `packages/cli/dist` with esbuild (npm dependencies stay external), copies every tree-sitter grammar `.wasm` file into `dist/grammars/` (so no `tree-sitter-*` npm package — each runs `node-gyp` on install — is a runtime dependency), and copies the built dashboard into `dist/dashboard/` (where `locateDashboardAssets` already looks). `npm pack` of `packages/cli` is then installed into a clean temp folder in CI and exercised end to end.

**Tech Stack:** esbuild (bundling), Node ≥ 20 ESM, pnpm 11 workspace, GitHub Actions, npm.

**Spec:** `docs/superpowers/specs/2026-10-30-codeloom-design.md` §2 (packaging: "Only `packages/cli` is published; `core` and the built dashboard are bundled into it"), §7 acceptance criteria 1–7 (esp. 3: real workspace; 6: "CI green; tarball installs and runs; UA notice included. npm publish only after the author approves").

## Real-app hardening (added 2026-11-03, author-approved after the Task 5 acceptance run)

The acceptance run on a real React UI + AdonisJS API workspace (local only; its code is never used in tests) found gaps that would hurt first users. Fix them before publishing. Tests use generic demo-shop-style snippets only (Customer/Invoice domain). The eval gate stays at 100% precision/recall; answer keys are never edited.

### H1 (precision): wrong table names marked `exact`
- Query-builder table args with an alias (`db.from('customers as c')`, `.join('invoices as i', …)`, `Model.query().from('x as y')`, `knex('x as y')`): the table is the part before ` as ` (case-insensitive), trimmed and unquoted.
- Raw SQL: names declared in a `WITH [RECURSIVE] name AS (` / `, name AS (` list of the same SQL string are CTEs, not tables — never report them. Table names inside SQL also drop `AS alias` / bare-alias suffixes and schema prefixes as today.
- A model imported under another name (`import { Customer as CustomerModel } from …`, default import with a different local name) resolves to the model class's `static table` (or naming convention) — never the local alias.
- Tests: each pattern → the real table, and no alias/CTE name appears anywhere in endpoints.json.

### H2 (coverage): UI HTTP calls through an axios instance or a request wrapper
- `const client = axios.create({ baseURL: … })` (exported/imported, incl. aliases) is an HTTP client: `client.get/post/put/patch/delete(url)` and **`client(config)` / `client({ method, url, data })`** are HTTP calls. Method from `config.method` (default GET); url from `config.url`.
- `config` may be an object literal argument or a `const config = { method, url, … }` declared earlier in the same function (follow one level).
- URL: template/concatenation with `${process.env.X}` / `import.meta.env.X` or a module const initialised from such an env var → base = that env name (matched against workspace `apiBase`), path = the rest; same `pathPattern` rules as today.
- A wrapper function that forwards a `{ method, url }` object to such a client (`httpClient({ method, url })`) is a wrapper (extend the existing wrapper inference: config-object parameter, not only a positional url).
- Confidence: as today (direct literal exact/param; through a wrapper ≤ param).
- Tests: each shape → the expected HttpCall with method/path/base; a page → hook → data function → `client(config)` chain links to the API route in a two-repo fixture with `apiBase` set.

### H3 (honest completeness): "complete UI → API → DB" only with a UI stop
- A chain is **complete** only if it has a UI stop (page or call) and reaches a store. A route-only chain that reaches a store is **API → DB** (new summary count `apiOnly`), not complete. `check` summary line: `N journeys: a complete UI → API → DB, b API → DB only (no UI caller), c missing the DB step, d broken at UI → API`, plus `routes with a UI caller: x/y`. `--fail-under` uses complete / (chains that have a UI stop) — document it. CheckReport gains `summary.apiOnly` and `summary.routesWithUiCaller` (+ total); version stays 1 (unreleased).
- Dashboard: the "Complete" pill/filter uses the same rule; route-only chains say "API → DB".
- Tests on demo-shop-style fixtures; update existing expectations with justification.

### H4 (precision): no guesses from built-in method names or tests
- The unique-method guess never fires for well-known built-in/ORM method names: Array/Map/Set/String/Promise/Object methods (`map`, `filter`, `forEach`, `reduce`, `find`, `some`, `every`, `includes`, `push`, `pop`, `shift`, `slice`, `splice`, `sort`, `join`, `concat`, `keys`, `values`, `entries`, `get`, `set`, `has`, `add`, `delete`, `clear`, `then`, `catch`, `finally`, `toString`, `trim`, `split`, `replace`, `startsWith`, `endsWith`), common ORM/query methods (`load`, `preload`, `merge`, `fill`, `save`, `create`, `update`, `delete`, `first`, `query`, `where`, `exec`, `findOrFail`, `findBy`, …) — keep the list in one exported constant.
- No guess when the receiver is known to be a local array/object literal, a `new` of a non-repo class, or a parameter typed as a non-repo type.
- Files under `test/`, `tests/`, `__tests__/`, `fixtures/`, `__mocks__/`, `*.test.*`, `*.spec.*` are never resolution targets for production code (a call from production code never resolves into them).
- Tests: `arr.map()` with a unique repo `map` method → unresolved (not guess); a production call that would only match a fixture's method → unresolved; eval gate unchanged.

### H5 (MCP): bounded tool responses
- `check_chains`: default returns the summary + top 20 items per kind; params `kinds?: CheckItemKind[]`, `limit?: 1..500 = 50`, `offset?: 0`; `truncated` + totals. `traces` unchanged.
- `list_chains`: default compact rows (`id, name, entry, routeKey, confidence, complete, journeys, stopCount, lanes: {ui,api,code,db,queue}, tables`), `detail: true` adds stops/unresolved.
- `get_journey`/`trace_route`/others: any single response above 1 MB of JSON is cut to fit with `truncated: true` and a message telling the agent which params narrow it (shared helper in `mcp/result.ts`).
- Tests: a synthetic 5000-chain map → every tool response < 1 MB; contract test schemas updated; the dashboard API keeps full data (it is local HTTP, not MCP).

### H6 (`check` noise)
- `unmatched-call` items dedupe by repo+file+line+callee (once, not once per chain) and skip calls on global built-ins (`console`, `JSON`, `Math`, `Object`, `Array`, `Promise`, `Date`, `Number`, `String`, `Reflect`, `setTimeout`, …) and the H4 built-in method names.
- `ui-no-route`/`ui-unreached` items group by call site: one item per call, detail lists the pages that reach it.
- Tests: duplicates collapse; built-ins skipped; grouped detail.

### H7 (hook + doctor)
- `init` writes a hook line that runs the **absolute path** of the codeloom bin that ran `init` (`process.argv[1]` resolved, quoted with `shellQuote`) when it exists, falling back to `codeloom` on PATH, falling back to nothing (no npx download in a hook).
- `doctor` warns when the hook's command cannot be found (path missing / not on PATH).
- `index` summary explains `files` vs `parsed` when they differ (e.g. "4 files had nothing to parse").
- Tests for each.
